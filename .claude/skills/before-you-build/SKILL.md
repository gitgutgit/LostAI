# before-you-build: 만들기 전에 과업을 넓히고 검증을 정한다

출처는 Felix Rieseberg의 착수 전 프롬프트(ALTITUDE, DEPTH, RANGE, VERIFICATION)다. 같은 글을 스킬로 옮긴 `be-ambitious`가 이 폴더 옆에 있다. 이 스킬은 그 방법을 해커톤 저장소의 작업 규칙(`init-collab`, `note-tracking`, `docs/ARCHITECTURE.md` 11절 P0/P1/P2)에 맞춰 줄인 판이다.

하루짜리 해커톤에서는 만들면서 고치는 쪽이 대개 빠르다. 이 스킬은 **크게 틀리면 되돌리기 비싼 일**에서만 몇 분을 써서, 엉뚱한 것을 잘 만드는 일을 막는다.

## 1. 과업 크기 정하기 (경로 0, 1, 2)

먼저 과업을 셋 중 하나로 나눈다. 애매하면 무거운 쪽으로 정하고, 작업 중에 커지면 올리기만 한다.

| 경로 | 기준 | 이 스킬에서 할 일 |
|---|---|---|
| **0 사소** | 한 파일, 되돌리기 쉬움, 계약 파일과 결과 숫자에 닿지 않음 (오타, 로그 문구, 내 note) | 아무것도 하지 않고 바로 만든다 |
| **1 한정** | 내 파트 폴더 안, 범위가 분명함, 데모나 숫자에 닿을 수는 있음 | 첫 보고나 note 작업 줄에 두 줄만 쓰고 기다리지 않고 진행: `진짜 목표:` (누구의 무엇이 달라지는가), `판단 밖 검증:` (실행, 측정, 채점 등 내 판단이 아닌 확인) |
| **2 구조** | 아래 중 하나라도 해당 | 이 문서 전부를 쓰고 진행 허가를 받는다 |

경로 2에 해당하는 것:
- 계약 파일(`server/events.py`, `server/model/docs.py`, `server/ops/registry.py`, `web/src/core/types.ts`)이나 루트, 문서, `.claude/` 변경 (`init-collab` §2)
- 다른 파트 폴더에 걸치거나 여러 파트가 같이 움직여야 하는 작업
- 결과 숫자의 기준을 바꾸는 변경: `server/agent/prompts.py`, 평가 대본, op 이름
- 한 시간 넘게 걸릴 작업, 시연 흐름이나 P0 범위를 바꾸는 작업
- 되돌리기 어려운 일: 동결 뒤 main merge, 실제 Google 문서나 Linear에 쓰기, 팀 밖으로 나가는 글, 돈이 드는 API 대량 호출
- 팀원의 작업 환경(공용 설정, 의존성, 실행 방법)을 바꾸는 일

발표 자료나 공지 같은 글은 입력(숫자, 결정)이 정해진 뒤에 쓴다. 이 스킬은 그 글을 쓰는 과업의 목표와 검증을 정하는 데까지만 쓴다.

## 2. 네 관점 (각 관점을 표나 짧은 줄로, 전부 합쳐 한 화면 안팎)

1. **진짜 목표.** '이 일이 끝나면 누구의 무엇이 달라지는가'를 한 줄로 쓴다. 기준은 대개 시연(말하면 문서가 바뀌고, 누가 말했는지 붙는다)과 `docs/ARCHITECTURE.md` 11절의 P0 항목이다. 이 일이 어느 P0를 움직이는지, P1이나 P2라면 지금 할 이유가 있는지 적는다. 글자 그대로의 요청과 다르면 둘을 나란히 적는다. **결과를 받는 사람이 요청한 팀원이 아니라 다른 사람(팀장, 다른 파트, 심사위원, 시연 관객)이면, 문서에서 추론한 그 사람의 의도는 가설로 표시하고 'OO가 실제로 묻는 질문은 무엇인가'를 확인할 질문 1순위로 올린다.** 의뢰인의 진짜 질문은 대개 요청 문장에 적혀 있지 않다. 이 목표를 혼자 추진하고 검증하는 데 필요한 접근과 준비(키, 로그, fixture, 시험 기기, 다른 파트의 엔드포인트)를 **이미 있는 것**과 **요청할 것**으로 나눈 표를 붙인다.
2. **숙련자라면.** 원자료는 실제 기록부터: 이벤트 로그(JSONL), `fixtures/` 녹화, `/stats` 지연 값, `results/` 측정 파일, `eval/` 채점 결과, git 이력, 팀원 note. 합성 시험은 보조다. 쓸 도구와 방법(측정 스크립트, 리플레이 재생, 여러 번 돌린 p50과 p95, 대조군)을 적는다. 어렵지만 닿을 수 있는 목표를 숫자로, 닿을 근거와 함께 쓴다(예: CLAUDE.md 목표 숫자 표의 말 → 화면 p50 2.5초 미만). 비용 추정(시간, 에이전트 수, API 비용)을 붙인다. 해커톤에서는 **시간이 가장 비싼 비용**이므로 동결 시각 안에 끝나는지 같이 적는다.
3. **동사, 다른 분야, 반박.** 과업을 명사가 아니라 동사로 다시 쓴다(결과를 쓰는 사람이 실제로 무엇을 할 수 있게 되는가). 이 일을 다르게 볼 분야 3~5개와 분야마다 **실제로 적용할 기법 하나**를 적는다. 사람 흉내는 하지 않는다. 말을 지어내지 않고 실제로 쓰이는 이름만 쓴다(예: 지휘관 의도, 사전 등록, 사후 검토, 과제 수행 측정, 레드팀). **반박 관점 하나는 반드시 둔다**: 이 일의 핵심 전제를 깨려는 시험이나 서브에이전트를 결과를 보기 전에 정한다. 코드 변경이면 PR 전에 `pr-review-toolkit:review-pr`를 돌리는 것도 여기에 들어간다.
4. **판단 밖 검증.** 내 판단이 아닌 것으로 끝났음을 보인다: 실행, 채점, 측정, 리플레이, 실제 사용. **결과를 실제로 쓰는 사람 쪽 지표를 최소 하나** 둔다(시연자가 말한 뒤 화면이 바뀌기까지의 시간, 다른 파트가 그대로 import해서 돌아가는지 등). 다른 팀원의 시간이 들면 상한을 적는다(예: 10분). 판정 규칙과 문턱은 실행 전에 적고, 결과를 본 뒤 바꾸지 않는다. 바꾸면 '개정'으로 표시하고 요청한 팀원에게 알린다. 그 지표의 **지금 값(기준선)** 을 한 줄로 적는다. 숫자에는 MOCK인지 LIVE인지 붙인다(MOCK 정확도는 의미가 없다). 결과가 바로 보이지 않으면(다른 파트 연결 뒤, 리허설 때) note에 `결과 확인: HH:MM (무엇을 볼지)` 한 줄을 남긴다.

## 3. 출력과 관문

- 네 관점 뒤에 **다시 쓴 과업 프롬프트**를 낸다. 이 프롬프트가 곧 작업 계획이다. 내 `notes/<GitHub 아이디>.md` 작업 항목 아래에 `의도와 검증` 두세 줄(진짜 목표, 판단 밖 검증과 문턱, 기준선)로 옮기고(`note-tracking`), 팀 전체가 알아야 하면 `notes/TEAM.md`의 공지와 요청 절 맨 아래에 한 줄 추가한다. PR을 열 때는 같은 내용을 PR 설명에 쓴다.
- **진행 허가를 받고 실행한다.**
  - 내 파트 안의 경로 2: 요청한 팀원(본인이 요청자면 파트 메인)에게 한 번 보여 주고 '진행'을 받는다.
  - 계약 파일, 루트, 문서, `.claude/`, 다른 파트 폴더에 닿으면: `init-collab` §4의 경고 → 승인 절차를 그대로 따르고, 팀장(지원, `gitgutgit`)이나 그 파트 메인의 확인까지 받는다. 이 스킬의 네 관점은 그 경고문의 '수정 이유', '영향 범위', '대안' 칸을 채우는 재료로 쓴다.
- 이미 팀장이나 파트 메인이 정해 준 과업을 실행할 때는 다시 묻지 않는다. 다만 의도와 검증이 적혀 있지 않으면 착수 직전에 이 스킬을 짧게 돌려 note에 `의도와 검증`을 써 넣고 진행한다. 과업 문장과 의도가 갈려 보이면 의도를 따르되, 그 판단을 note `메모`에 한 줄 남기고, 공용 영역에 닿을 때만 묻는다.
- 경로 2 작업을 닫을 때 note에 사후 검토 네 줄(계획한 것, 일어난 것, 차이, 이유)을 남긴다. 다음 사람이 같은 실수를 하지 않게 하는 가장 싼 방법이다.

## 4. 이 스킬이 막으려는 실패

다른 프로젝트에서 실제로 있었던 사례를 일반화했다.

| 실패 | 관점 |
|---|---|
| 요청 문장(기록 소급)을 글자 그대로 연결 작업으로 집행했다. 요청자의 의도는 체계 전체의 합리성 점검이었다 | 진짜 목표 |
| 성공 지표가 작업한 쪽의 호출 수뿐이었다. 결과를 쓰는 사람 쪽 지표는 정의조차 없었다 | 판단 밖 검증 |
| 실사용 원자료(실제 세션 기록 수십 건)가 있었는데 합성 질문으로 쟀고 원문도 남기지 않았다 | 숙련자라면 |
| '이름을 바꾸면 찾기가 빨라진다'는 전제를 깨 보지 않았다. 재측정에서 뒷받침되지 않았다 | 반박 |
| 가장 큰 개선은 계획 밖, 결과를 쓰는 사람의 실제 경험에서 나왔다 | 진짜 목표, 동사 |

이 저장소에서 같은 실패는 예를 들어 이런 모습이 된다: 라우터 정확도를 올리려고 프롬프트를 고쳤는데 시연에서 중요한 것은 지연이었다(진짜 목표), MOCK에서 잰 숫자로 개선을 주장했다(판단 밖 검증), 평가 대본 작성자가 프롬프트를 보고 대본을 썼다(반박이 무너짐).

## 5. 글쓰기

팀원에게 내는 글은 한국어로 쓴다(커밋 메시지는 저장소 규칙의 영역 태그를 따른다). 내부 코드명이나 약어는 내용을 먼저 쓰고 괄호에 붙인다. 파일은 저장소 기준 경로로 적는다. 비밀 정보(`.env`, 키, Google 문서 ID, 터널 주소)는 계획이나 note에 적지 않는다.
