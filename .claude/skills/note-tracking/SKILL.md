# note-tracking — 본선 작업 노트

각 팀원은 **`notes/<GitHub 아이디>.md` 하나**에 하는 일을 체크리스트로 계속 기록한다.
Claude는 작업하면서 이 파일을 **자동으로 갱신**한다. 따로 요청하지 않아도 된다.

note는 세 사람이 읽는다.
1. **다음 세션의 나 / 다음 Claude** — 대화가 끊겨도 note만 읽고 바로 이어간다.
2. **다른 컴퓨터의 팀원** — 내 note를 열면 맨 위 몇 줄로 "지금 뭐 하는지, 어디서 막혔는지, 숫자가 어떤지"를 안다.
3. **팀장(지원)** — 네 개의 note를 모아 P0/P1/P2 진행 현황을 본다.

---

## 1. note 파일 위치

| 사람 | GitHub | 파트 | note 파일 |
|---|---|---|---|
| 지원 (팀장) | `gitgutgit` | 총괄 · 공용 계약 | `notes/gitgutgit.md` |
| 한서 | `77SONNY77` | 기능 (메인) | `notes/77SONNY77.md` |
| 태우 | `Mal-Mi-Jal` | 서버·UI (메인) | `notes/Mal-Mi-Jal.md` |
| 주현 | `ProfessionalSeaweedDevourer` | 기능 (서브), 서버·UI (서브) | `notes/ProfessionalSeaweedDevourer.md` |

- 누가 어느 파트인지는 `init-collab` §1 표를 따른다. 현재 작업자 확인 방법도 거기 있다.
- **사람마다 파일 하나**다. 같은 파일을 둘이 고치면 git 충돌이 나기 때문이다. 파트를 둘 맡은 사람(주현)은 한 note 안에서 항목마다 파트 태그(`[기능]`, `[서버·UI]`)를 붙인다.
- 계약 파일이나 다른 파트를 고친 기록은 **고친 사람의 note**의 `다른 영역 관련`에 남긴다.
- 파일이 없으면 §3 템플릿으로 **새로 만든다.**
- **공용 노트 `notes/TEAM.md`**: 일정·P0 현황·결정 사항·계약 변경 기록·공지. `결정 사항`·`계약 변경 기록`·`P0 현황`은 팀장(gitgutgit)만 고치고, 다른 팀원은 `공지 · 요청`에 맨 아래 한 줄 추가만 한다. 세션 시작 시 내 note와 함께 읽는다.

## 2. 언제 갱신하나

| 시점 | 할 일 |
|---|---|
| **세션 시작** | 내 note를 읽고 `현재 목표`와 `진행 중`을 사용자에게 2~3줄로 요약한 뒤, 이어서 할지 물어본다. note의 `마지막 업데이트` 이후 **계약 파일이 바뀌었는지** 확인해서 바뀌었으면 함께 알린다. (`git log --since="<마지막 업데이트>" --oneline -- server/events.py server/model/docs.py server/ops/registry.py web/src/core/types.ts`) |
| **작업 시작** | `진행 중`에 항목을 추가하고 앞에 `(P0)` `(P1)` `(P2)`를 붙인다. 기준은 `docs/ARCHITECTURE.md` 11절. 큰 작업은 하위 체크리스트로 쪼갠다. |
| **하위 단계 완료** | 해당 항목을 `[x]`로 체크한다. |
| **실행·측정 결과가 나옴** | `최근 결과`를 새 숫자로 바꾼다. 이전 숫자와 비교해 의미 있게 바뀌었으면 `메모`에 이유를 한 줄 남긴다. |
| **작업 완료** | `진행 중`에서 빼서 `완료`의 오늘 날짜 아래로 옮긴다. 바뀐 파일 경로와 핵심 숫자를 적는다. P0 항목이면 맨 위 `한 줄 상태`에도 반영한다. |
| **막힘 / 보류** | `[ ]`를 `[!]`로 바꾸고 이유를 적는다. 맨 위 `한 줄 상태`도 🟡로 바꾼다. 다른 사람 때문에 막혔으면 누구인지(GitHub 아이디) 적는다. |
| **다른 영역 요청 · 수정** | `다른 영역 관련`에 기록한다. (`init-collab` §4 승인 절차와 연동) |
| **나중에 할 일이 생김** | `할 일`에 추가한다. |
| **세션 종료** | `마지막 업데이트`와 `한 줄 상태`를 고치고, 다음에 바로 할 일을 `현재 목표`에 **실행 가능한 형태**로 남긴다. (예: "`fixtures/Mal-Mi-Jal_sprint.jsonl` 재생해서 탭 배지 숫자 확인") |

갱신은 **작업 흐름 중에 바로바로** 한다. 마지막에 몰아서 쓰지 않는다. 세션이 갑자기 끊길 수 있고, 해커톤 당일에는 팀장이 수시로 note를 모아 본다.

## 3. 포맷 (템플릿)

```markdown
# Note — <이름> (<GitHub 아이디>) · <파트> <메인/서브>

> 마지막 업데이트: YYYY-MM-DD HH:MM
> 한 줄 상태: 🟢 진행 중 / 🟡 막힘 / ✅ 마무리 / ⚪ 대기 — <지금 상태를 한 문장으로>
> 실행: `<내가 주로 돌리는 명령>`  ·  모드: MOCK / LIVE (<라우터 모델> → <에디터 모델>)

## 현재 목표
- <지금 집중하는 목표 1~2줄. 세션 종료 시 "다음에 바로 할 일"로 갱신>

## 최근 결과
| 지표 | 값 | 목표 | 언제 · 모드 | 결과 파일 |
|---|---|---|---|---|
| <예: 말 → 화면 p50> | <2,4초> | <2.5초 미만> | <11-09 14:20 · LIVE haiku→sonnet> | `results/<GitHub>_latency_1109_1420.json` |

## 진행 중
- [ ] (P0) <작업명> (시작: HH:MM)
  - [x] <완료한 하위 단계>
  - [ ] <남은 하위 단계>
- [!] (P1) <막힌 작업> — 사유: <이유> · 기다리는 사람: <GitHub 아이디>

## 할 일
- [ ] (P2) <나중에 할 작업>

## 다른 영역 관련
- [ ] <대상 파일> — <요청·수정 내용> → <승인자 GitHub 아이디> (상태: 요청함 / 승인 대기 / 승인됨 / 완료)

## 완료
### YYYY-MM-DD
- [x] (P0) <작업명> — `<바뀐 파일 경로>` (<핵심 숫자가 있으면 함께>)

## 메모
- <결정 사항, 알게 된 점, 숫자가 바뀐 이유, 참고 링크>
```

### 파트별 `최근 결과` 지표 예시
| 파트 | 지표 |
|---|---|
| 기능 · 에이전트 | 라우터 정확도(정답 라벨 대비), edit·command를 ignore로 놓친 수, 에디터 op 정답률, 라우터·에디터 ms |
| 기능 · 손 인식 | 입장 관문 통과율과 평균 통과 시간, 손동작별 오인식 수, 인식 fps, 확대·축소 반응 지연 |
| 서버·UI | 말 → 화면 p50/p95, Google 동기화 성공률과 ms, 브로드캐스트 지연, 화면 프레임 끊김 여부 |
| 총괄 | P0 완료 수 / 전체, 데모 리허설 통과 여부, 남은 위험 |

### 체크 표기
- `[ ]` 할 일 / 진행 중
- `[x]` 완료
- `[!]` 막힘·보류 (반드시 사유를 적는다)

### 작성 규칙
- **`최근 결과`에는 숫자를 직접 적는다.** `results/`는 `.gitignore`에 있어서 다른 컴퓨터에서는 결과 파일이 보이지 않는다. 파일 경로는 "내 컴퓨터 어디에 있는지" 참고용이다.
- 숫자에는 **모드(MOCK/LIVE)와 모델**을 꼭 붙인다. 손 인식 숫자에는 **환경(조명, 카메라, 노트북)**을 붙인다. 조건 없이 적힌 숫자는 비교에 쓸 수 없다.
- `server/agent/prompts.py`, 평가 대본, op 이름이 바뀐 뒤의 결과라면 `메모`에 "<시각> 이후 기준 변경"이라고 적는다. 이전 숫자와 섞어서 비교하지 않기 위해서다.
- 항목은 **한 줄에 한 작업**. 무엇을 했는지 알 수 있는 동사로 쓴다. (예: `확대 모드를 브이 0.5초 유지로 켜기`)
- 함수·파일 이름은 백틱으로 감싸고 실제 이름을 쓴다.
- `완료`는 **최신 날짜가 위**에 오게 쌓는다. 해커톤 당일에는 날짜 대신 시각(`### 11-09 14:00~`)으로 나눠도 된다.
- `완료`가 약 100줄을 넘으면 오래된 부분은 `notes/<GitHub>-archive.md`로 옮긴다.

## 4. 다른 사람 note 읽기

"태우는 지금 어디까지 했어?", "다들 진행 상황 어때?" 같은 질문을 받으면:

1. 해당 사람의 note를 읽는다. 전체 현황이면 `notes/` 아래 네 개를 모두 읽는다.
2. 각 note의 `한 줄 상태`, `현재 목표`, `[!]` 항목, 남은 `(P0)` 항목, `최근 결과`, 나와 관련된 `다른 영역 관련`만 뽑아서 요약한다.
3. `마지막 업데이트`가 오래됐으면 "업데이트가 <시각>에 멈춰 있음"이라고 함께 알린다. 해커톤 당일에는 **2시간 이상**이면 오래된 것으로 본다. note가 실제 상태와 다를 수 있다.
4. 전체 현황은 이런 형태로 보여준다. 팀장이 물으면 맨 아래에 **P0 전체 진행률**과 **막힌 의존 관계**(누가 누구를 기다리는지)를 붙인다.
   ```
   | 사람 | 파트 | 상태 | 지금 하는 것 | 남은 P0 | 최근 결과 | 막힘 |
   |---|---|---|---|---|---|---|
   | 한서 | 기능 메인 | 🟢 | 입장 관문 손동작 3개 | 확대 모드 | 통과율 9/10 (밝은 실내) | — |
   | 태우 | 서버·UI 메인 | 🟡 | B 캔버스 탭 | Google Sheets 동기화 | p50 2.9초 (LIVE) | events.py 필드 확정 대기 (gitgutgit) |
   ```

## 5. 금지 · 주의

- **다른 사람의 note는 수정하지 않는다.** 읽기만 한다. 고칠 내용이 있으면 그 사람에게 알리거나, 내 note의 `다른 영역 관련`에 적는다.
- note에 **API 키, 토큰, `.env` 값, Google 문서 ID·URL, 시연용 터널 주소 같은 민감 정보는 적지 않는다.** (`init-collab` §6)
- note는 **기록용**이다. 코드나 긴 로그를 붙여넣지 말고, 파일 경로·숫자·요약만 적는다. 에러는 핵심 한 줄만 적는다.
